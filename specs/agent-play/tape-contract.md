# The Run-Start Tape Contract (tape v2) — what a proof must carry
### Status: RATIFIED 2026-08-15 (attended, from the s1796 fidelity matrix; one-tape-per-life owner-ruled same day) · the format law the assay worker verifies against · companion to `specs/agent-play/assay-worker.md`

## Why (measured, not argued — the s1796 matrix)
The fidelity matrix (`e2e/assay-replay-roundtrip.spec.ts`, lane-d `2ba06e494`) isolated the divergence class exactly:
- Fresh single-life tapes reproduce byte-for-byte ✓ (cell b). Death-restart tapes reproduce ✓ (cell c) — **one-tape-per-life already exists**: `resetRun()` cuts a fresh recorder (`RunManager.ts:327`, `Game.ts:6440`). The owner's ruling ("one tape per life makes the most sense") is satisfied by shipped behavior and this contract PINS it as law.
- **The real gap: progression.** Live boot applies saved meta progression (`RunManager.ts:86`; Territory-I changes starting build credits, `Game.ts:7285`) while the replay boot exits before installing `RunManager` (`Game.ts:2209`). A controlled Territory-I tape diverges on a fresh single life (`d6ceecd8` vs `168dafd5`); both live reels diverge because both players are progressed. **A tape that does not declare its starting state does not describe its run.**

## The contract
1. **One tape = one life** (law, already mechanical): a tape begins at run birth and ends at that life's terminal; a death-screen restart cuts a new tape. No tape spans lives.
2. **Tape v2 adds `runStart`** — the progression state the run began under, in the shape the game has ALREADY proven sufficient for booting identical progressed state across machines: the multiplayer room-setup progression payload (`normalizeSetup`'s `meta` + `research`, `functions/api/_multiplayer.ts`; live-verified in room inspect: `meta{version, tracks{territory, science, hero, agent}}`, `research{version, epochId, metaScienceCursor, progress, taken[]}`). **Reuse that shape verbatim — do not invent a sibling schema.** (Medals are deliberately NOT included: no currently-assayable contract's sim reads them headless; extend `runStart` the day one does, with a version bump.)
3. **The recorder captures `runStart` at run birth** (`startRunTape`), from the same live state `RunManager` just applied — recorded, never re-derived later.
4. **Replay applies `runStart` before boot**: the replay path installs the run under the tape's declared progression (seed the storage / RunManager with `runStart` — the same apply mechanics the MP guest path and the campaign harness's profile injection already use). Replay of a v2 tape MUST reproduce its recording byte-for-byte; that is the assay's verify condition.
5. **The declaration is part of the claim**: the assayer verifies that the OUTCOME follows deterministically from the DECLARED inputs (seed + runStart + input log). A fabricated `runStart` produces a replay of that fabricated state — the outcome still has to follow. Ranking fairness across progression levels is unchanged county law (progressed players already rank alongside fresh ones); the tape just stops lying about which game was played.
6. **Bounds**: `runStart` adds ~1–2 KB (four int tracks + the taken-nodes list). The 64 KB tape cap is UNCHANGED; `validateTape` (v2) requires `runStart` well-formed and within the same total cap.
7. **Legacy (v1) tapes are structurally unverifiable** — they omit `runStart`, so no replay can be faithful to an unknown starting state. No retro-fill is possible honestly.

## ADDENDUM 2026-08-22 — what the door's first live assay measured (F-ASSAY-E2E-1/2/3)
Nothing above is retracted; this records three facts the contract did not yet name, each measured by a live production probe (`artifacts/assay-e2e-20260822/`) and cured on the same evidence.

1. **The headless door writes v2** (F-ASSAY-E2E-1). `scripts/gr-sim.mjs` hardcoded `version: 1` and no `runStart`, so every run through the public door was refused as "legacy tape v1 is unverifiable" whatever it played. §3's "captured at run birth, recorded, never re-derived" now has a headless implementation: `HeadlessContractSim.runStart` (a read-only field set in the constructor from the meta `RunManager` just installed plus the research state read at the top of it) and the tape writer copies it. A solo door boot is a virgin profile and reads exactly what `RunTapeRecorder`'s own default writes for one; a campaign-harness boot, which injects storage, reads ITS state.
2. **A terminal-instant order needs a tick to live on** (F-ASSAY-E2E-2). The browser recorder samples BEFORE each step, so its last entry is always at `durationTicks - 1`, and both validators enforce `t < durationTicks`. gr-sim's rider may answer AT the boundary — an accepted `SECURE_CHOICE` is stamped `round(timeAlive * 30)`, which equals the elapsed tick count exactly, and the county returned HTTP 400 `bad_payload` for it; only silence could be submitted. The recorded tick is the truth (that order is what secured the claim, and moving it earlier replays into a closed secure window). The elapsed count was the wrong side: an input log whose last input causes the terminal runs one tick past the last step, so gr-sim now declares `durationTicks = max(elapsedTicks, lastEntryTick + 1)`. Neither validator moved — the refused exhibit is still refused.
3. **§4's "replay applies runStart before boot" is ENGINE-RELATIVE — a door tape can only be replayed by the door's engine.** Measured on `the-claim` / `e1-the-claim-01` at tick 0, before any order: gr-sim shows `gold-seam-1 @anchor4 (18,-7)`, `gold-seam-2 @anchor1 (-9,6.7)`, `gold-seam-3 @anchor3 (7.5,6.5)` all live; the browser shows seam-1 identically, seam-2 at `@anchor5 (25,6.9)`, and seam-3 dark. Two live seams against three, and a shared id at a different anchor. So `scripts/assay-replay.mjs` now routes by the tape's own content — `agent_orders` entries mean `HeadlessContractSim` (`scripts/assay-replay-agent.mjs`), anything else means the browser — using the same discriminator the browser replay seam already computes at `Game.ts:6892`. **LAW: a tape is assayed by the engine that recorded it.**

**STILL OPEN, for the owner.** A browser replay of a door tape remains impossible, and two further browser-side defects were pinned while proving it, both of which would bite a BROWSER-recorded agent tape (a human who rides with standing orders) exactly as they bit the control: (a) the solo upgrade-draft clock is WALL-CLOCK (`Game.ts:9158`, `performance.now() + Balance.offers.pickSeconds`) while `levelup` freezes the sim clock, so a compressed headless replay — 300 sim-seconds in ~6 wall-seconds — never expires the draft and the run stalls at the first level-up forever; (b) `tickStandingOrders` runs only inside the `simActive` branch (`Game.ts:2773` → `:2960`), and `simActive` is false in `levelup` (`GameState.ts:22`), so a recorded `PICK_UPGRADE` can never execute even if the draft did expire. Measured: the v2 control froze at `timeAlive 23.87` in `levelup` and played its remaining 8,000 ticks against a stopped clock. Neither is touched here; both want a slice of their own.
