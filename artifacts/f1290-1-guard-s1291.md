# F-1290-1 — the blocker-panel guard, and what measuring it revealed

**s1291, 2026-07-31.** s1290 struck five stale rows out of the dashboard's blocker panel and
left the guard owed, with a design constraint: *do not re-implement either rule* (F-1261-1 — a
second implementation of a ledger rule disagreed with the first on 4 of 14 rows).

## What shipped

`scripts/blocker-panel-closed-guard.mjs` — fails when the panel is showing the owner a row
whose F-ID the ledger has closed. It **executes** both existing rules and copies neither:

| rule | source | how |
|---|---|---|
| panel selection + display truncation | `scripts/dashboard-gen.sh` | the `done < <(...)` and `txt=$(echo "$line" \| ...)` lines are extracted by anchor (never by line number) and run through `bash` |
| closure state | `scripts/findings-state-guard.mjs` | `scan()` imported |

`scan()` is now exported and the module no longer self-executes on import
(`process.argv[1]`-guarded main). Behaviour on direct invocation is unchanged: **151 / 125 / 26,
double-state 0, PASS** — byte-identical to the pre-refactor run.

## The refutation that changed the design

Built against the narrow census, the guard ran on the pre-strike ledger (`2e02098f`) and
reported **15 panel rows, 0 violations**. It did not catch the incident it was written for.

Cause, measured rather than guessed — all five struck findings were **ABSENT from the census
entirely** before the strike, not "open":

```
F-1024-4 | pre-strike: ABSENT | now: closed[1390]
F-1212-3 | pre-strike: ABSENT | now: closed[1336]
F-1217-1 | pre-strike: ABSENT | now: closed[2140]
F-1030-2 | pre-strike: ABSENT | now: closed[1462]
F-1217-2 | pre-strike: ABSENT | now: closed[2141]
```

They became "closed" only because s1290's strike rewrote the original lines *into* the census's
narrow vocabulary. A guard composed of the panel rule and the narrow census can therefore never
fire from that pathway: the same edit that makes the census see a closure is the edit that makes
the panel drop the row.

### The census reads a vocabulary, not the ledger

| shape | occurrences in current BACKLOG | census sees |
|---|---|---|
| bullet-led `- ✅ **F-x …` | **136** | **1** |
| bare-led `✅ …` | 133 | 133 |

**56 F-IDs are declared closed only by a row the census cannot read.** Every fire's reported
"125 closed" is denominated in a vocabulary that misses the ledger's commonest closure shape.
This is filed as **F-1291-1** (open — widening the default needs the triage the guard's own
header demands; it is not a drive-by).

So the guard opts into a `closedVocabulary: 'wide'` reading — one implementation, two documented
vocabularies, **default deliberately unchanged**. Wide widens *closed* only, never *open*: the
panel row is itself the open claim.

## What the guard is worth — stated honestly

With the wide vocabulary, against the pre-strike ledger:

```
panel rows : 15   closed-on-panel : 1   rc=1
F-1030-2  closed at BACKLOG:1461
    panel row: ⚠️ F-1030-2 (REAL, small, NEW …) — `m2-05:198` is intermittently r
```

**It would have caught 1 of the 5 rows, not 5.** The other four had *no closure line in BACKLOG
at all* — s1290 verified them against `.claude/settings.json`, a `goals.json` leaf, and prior
rulings. A guard that reads only the ledger is structurally incapable of seeing a finding closed
in the code. That is a real limit, stated here so no one inherits this guard believing the panel
is now trustworthy.

The one it catches is exactly the structural case s1290 named — closure **appended below** the
open row, which the per-line exclusion can never reach:

```
:1459  - ⚠️ **F-1030-2 (REAL, small, NEW …)**            <- panel draws this
:1460
:1461  - ✅ **F-1040-1 / F-1030-2 UPDATE (s1040 drain …)** <- closure, invisible to the panel
```
