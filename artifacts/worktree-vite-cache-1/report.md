## Root cause, read in the code (vite 8.3.0, `node_modules/vite/dist/node/chunks/node.js`; line numbers from that file)
**1. One cache for the whole Mac, keyed by checkout.** With no `cacheDir`, vite uses `<package dir>/node_modules/.vite` (`:37041`); every worktree's `node_modules` is a symlink to the primary's, so every checkout resolves the same physical directory. The cache's identity hashes `config.root` (`getConfigHash` at `:28396`, `root: config.root` at `:28401`), so a boot from any other checkout finds a foreign hash, logs "Re-optimizing dependencies because vite config has changed" (`:27876`) and deletes `deps/` (`fsp.rm` at `:27884`). A server whose pre-bundled files were deleted answers the browser's next `?v=` request with 504 `Outdated Optimize Dep` (the missing file throws at `:25338`, `throwOutdatedRequest` at `:25350`, the 504 is written at `:19876` to `:19881`), and `src/main.ts:202`'s dynamic `import('./game/Game')` fails. Node guards count as boots: `createServer` in middleware mode initialises the client optimizer (`initServer(false)` at `:24572`, `depsOptimizer?.init()` at `:36375`), and about forty guards call it with the repo config (for example `scripts/standing-orders-module-split.test.mjs:11`).

**2. The scan dies on an art-store page.** With no `optimizeDeps.entries` vite globs `**/*.html` under the root (`computeEntries` at `:27472` falls through to `globEntries("**/*.html")`, `globEntries` at `:27519`) through tinyglobby, whose `followSymbolicLinks` defaults to `true` (`node_modules/tinyglobby/dist/index.mjs:271`), so it walks the `assets/pilots` symlink into the art store and reaches `assets/pilots/hero-3d/compare.html`. That page's `tsconfig.json` is `{"extends": "../../../tsconfig.json"}`; from the store's real directory (`/Users/robin/Claude/Projects/GoldRush-assets/pilots/hero-3d`) that is `/Users/robin/Claude/Projects/tsconfig.json`, which does not exist (from the symlinked path it would be the checkout's own tsconfig). Rolldown's scan fails with `[TSCONFIG_ERROR] Failed to load tsconfig '../tsconfig.json'` (that string is the missing path relative to the checkout root, measured: `path.relative(<checkout>, <missing>)` = `../tsconfig.json`), vite logs "(!) Failed to run dependency scan. Skipping dependency pre-bundling." (`:35204`), and every cold boot finds the six deps at runtime and full-reloads the page ("optimized dependencies changed. reloading" at `:35328`, `fullReload()` at `:35330`).
- **Correction to the master's premise:** it is not "the real path of the shared modules"; it is the art store's page reached through `assets/pilots`, and it is not worktree-only: the primary's server logged the same error, plus `'worktrees/tsconfig.json'`, because its glob also walked every lane and gate worktree (145 html entries, 123 of them under `worktrees/`; this worktree's glob had 21).
- **Attribution by measurement** (`before/scan-attribution.log`, each set in a private scratch cache, the shared cache untouched): default glob **FAILED** `[TSCONFIG_ERROR]`; `assets/pilots/hero-3d/compare.html` alone **FAILED**, same error; the other 20 html files together: **ok**, 6 deps; `index.html` + `src/replay/harness.html`: **ok**, the same 6 deps (`lil-gui`, `meshoptimizer`, `three`, `three/addons/utils/BufferGeometryUtils.js`, `three/examples/jsm/loaders/GLTFLoader.js`, `three/examples/jsm/math/ConvexHull.js`), exactly the six the uncured boots discovered at runtime.

## The cure (firewall: `vite.config.ts`, `.gitignore`, `scripts/attended/README.md`, this folder)
1. **`cacheDir: path.resolve(import.meta.dirname, '.vite-cache')`** in `vite.config.ts`. Resolved from the config file's own directory, never `process.cwd()`: vite's config bundler defines `import.meta.dirname` per module as that module's own directory (`:37370` and the injected `const __vite_injected_original_dirname = ...` at `:37421`). Measured: loaded through `artifacts/worktree-vite-cache-1/vite.no-entries.config.ts` (a config one folder deep that imports `../../vite.config`), the cache still landed at the checkout root, not in the importing folder. Vite's watcher already ignores its own `cacheDir` (`:16359`). `vite build` reads `cacheDir` only in watch mode (`:34052`), and the build proof below shows it.
2. **`optimizeDeps.entries: ['index.html', 'src/replay/harness.html']`**, the smallest thing that makes the scan succeed, and the reason, measured: a control arm with the per-checkout cache but WITHOUT entries (`control-no-entries/`, three fresh cold boots) still failed the scan on `[TSCONFIG_ERROR]` 3 of 3 and full-reloaded the page before boot 3 of 3; with the entries, 0 reloads in 7 of 7 cured boots. These are the two tracked html pages with module scripts (the others: `public/privacy.html` has no script, `site/*.html` and `scripts/stream-*.html` carry no module imports of dependencies); `src/replay/harness.html` is booted by five e2e specs (`e2e/e4-roads-and-convoys.spec.ts:26`, `e2e/e7-playbook-rows.spec.ts:27`, `e2e/true-reel-harness.spec.ts:27`, `e2e/lantern-true-world.spec.ts:189`, `e2e/e3-moth-season.spec.ts:13`). `entries` is not part of vite's cache hash (`:28396` to `:28425`). For the next reader: a new html page that imports dependencies belongs in this list; until it is added, its first cold load discovers its extra deps at runtime and reloads once (the control arm's behaviour, a reload rather than a failure, now that the cache is private). No `esbuild`/`tsconfigRaw` setting was needed and no dependency was added. A `vite:deps` debug boot shows it plainly (`after/after-scan-debug-5326.log`): "Crawling dependencies using entries: .../index.html, .../src/replay/harness.html", "Scan completed in 197.37ms", "using post-scan optimizer result, the scanner found every used dependency", "dependencies optimized" at +459 ms.
3. **`legacyDepsUrlPlugin()`**, a dev-only (`apply: 'serve'`) middleware in `vite.config.ts`, needed because the cure would otherwise break a spec: `e2e/e5-sea-contact.spec.ts:46` (and five `scripts/review-*.mjs`) import three.js in the page from the literal `/node_modules/.vite/deps/three.js`. It rewrites that prefix to wherever `cacheDir` points; while `cacheDir` is still `node_modules/.vite` the two are equal and it registers nothing (proved on the shim-only commit `0f32f5107` by calling its `configureServer` against the resolved config: 0 middlewares). It is committed first so no commit on this branch has the moved cache without it. Measured with `legacy-url-check.sh` (the literal URL, then the spec's one test that uses it, default config, desktop-chrome):

## Findings
- **F-WVC1-1 (premise corrected, non-blocking):** the scan failure is not caused by "the real path of the shared modules" but by the art store's `pilots/hero-3d/tsconfig.json` (`"extends": "../../../tsconfig.json"`, reached through the `assets/pilots` symlink and resolved from the store's real path to the absent `/Users/robin/Claude/Projects/tsconfig.json`); it fails in the primary as well, where the default glob also walks every worktree under `worktrees/` (145 entries). Named entries cure it here; the store file is outside this repository and was not touched. The store's owner may still want that tsconfig fixed for anyone who scans the store directly.
- **F-WVC1-2 (hardcoded optimizer address, carried by the rewrite):** `e2e/e5-sea-contact.spec.ts:46` and `scripts/review-{enemy-sprites,land-yacht,prospector-sprites,sprite-idle,toaster-sprites}.mjs` import `/node_modules/.vite/deps/three.js`, vite's private cache address. On clean main that test is ALREADY red whenever another checkout has just emptied the shared cache (the uncured control above: 404, failed); the cure would have made it deterministically red; `legacyDepsUrlPlugin` makes it deterministically green.
