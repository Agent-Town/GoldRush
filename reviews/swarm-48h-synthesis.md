## 1. Ranked findings

### Tier 1 — HIGH: permanent player-data loss (cloud sync)

**H1. A stale device silently overwrites a newer cloud save — no compare ever happens after boot.** `src/game/AccountSync.ts:79` — the only boot-time cloud read fires solely when local state is *absent*; the compare/conflict flow exists only inside explicit sign-in. Any profile-data write on a stale device — including just clicking your profile name, which writes no gameplay data — schedules an unconditional push with no savedAt precondition, and the server replaces `current` unconditionally (`functions/api/_accounts.ts:190-208`). Play on the tablet in the evening, open the laptop in the morning: the laptop's first write destroys the evening's progress while showing "ledger backed up ✓". The rotated server versions (`:v1..:v5`) are unreachable from any UI, so after five more pushes the newer save is gone forever. This is the core multi-device use case of the feature, sessions last 30 days on both devices, and the default profile id is shared — the trigger is everyday behavior, not an edge case.

**H2. Cloud restore wipes all 17 profile keys before writing, with no rollback and a false reassurance message.** `src/game/ProfileTransfer.ts:95-107` — `restoreProfileBundle` commits the profile-state switch (`:95`), then `removeItem`s every per-profile data key (`:97`), then writes cloud values one key at a time with a per-key try/catch that bails mid-loop. A quota throw (envelopes legitimately run to ~190KB) leaves the profile half-deleted/half-cloud with the switch already committed; the surfaced error says "your ledger stays safe here," which at that moment is false — and steers the player toward "keep local," which then force-pushes the gutted profile over the still-good cloud copy. Gated on a mid-write storage failure, so high rather than critical, but when it fires the loss is total and unrecoverable.

### Tier 2 — HIGH: the new multiplayer mode cannot hold sync (Law 1 cluster)

These five findings share one shape: the lockstep sim is fed by things that are not in the lockstep stream. Each one alone guarantees desyncs in a real ride; together they make "Ride Together" — which is a plain player-facing town card, not dev-gated — effectively unplayable for organic pairs. The desync auto-recovery keeps sessions from permanently corrupting, but findings H5/H6 show the recovery itself cannot converge, so the practical result is a "wire crossed" pause-card loop.

**H3. Every level-up in co-op guarantees a desync; a family of DOM inputs mutates the sim on one client only.** `src/game/Game.ts:1313` consumes the lockstep tick before any gating; the upgrade pick (`Game.ts:3556`), HUD pause button, death-overlay "Try Again", secured-choice buttons, and the baron-ceremony skip (raw window listeners) all apply directly from local clicks — none has a lockstep channel (`src/mp/LockstepClient.ts:4-18`). Both players freeze on level-up, each clicks at their own wall-clock moment, tick consumption diverges from tick simulation, and `progression.stacks`/`timeAlive` are hashed. Keyboard pause IS lockstep-routed, proving the DOM paths are oversights. Expect a desync-pause-rollback roughly every level-up — about once a minute in this genre.

**H4. Mouse building bypasses lockstep entirely and resolves position from the local camera.** `src/systems/BuildSystem.ts:392` registers a raw canvas click whose handler (`:1003`) confirms a build directly — spending gold and placing a building on one client only. Even the routed confirm resolves the ghost from the *local* pointer raycast through the *local* per-player camera, so identical confirm ticks place at different coordinates. Gold, economy log length, and building positions are all hashed. The same range de-pointered blast aim for MP but left builds untouched. Any desktop mouse user desyncs the ride on every placement — of a core mechanic.

**H5. Desync recovery restores identical state but not identical time, so it cannot converge under real latency.** `src/mp/LockstepClient.ts:227-233` — the snapshot handler ignores the snapshot's tick (which the relay sends), never rewinds `nextSimTick`/bundles, and the relay can't replay flushed inputs. Clients pause at whatever tick the hash happened to arrive on, restore the same state, then resume applying *different* input suffixes — `timeAlive` is hashed at 1/30s granularity, so ≥1 tick of skew re-desyncs within a second: a loop, each iteration re-showing the pause card. Detection is also one-sided (`:223-224` drops peer hashes with no local counterpart), and the paused leader stops sending inputs, starving the innocent peer. The e2e passes only because localhost Chromium×Chromium is the lucky symmetric case and it never asserts post-recovery hash equality.

**H6. Roster changes apply at websocket arrival, not tick-aligned; the relay accepts mid-run joins.** `src/mp/LockstepClient.ts:210-212` mutates the roster synchronously; `Game.syncMultiplayerActors` then creates/teleports/hides actors *inside the sim tick*, feeding enemy targeting — and peers consume buffered ticks at different depths, so the same broadcast lands at different sim ticks. The relay has no "game started" gate (`functions/api/_multiplayer.ts:173`), and worse, the player-facing join flow's `probeRideRoom` does a full join-then-close just to validate a phrase — so a third friend *typing the code* mid-run churns the running pair's roster and desyncs them. Worst case (one peer consumes zero ticks in the window) is a permanent actor-count mismatch resync cannot heal.

**H7. No shared-setup handshake: contract, seed, difficulty, meta defenses, and research are per-client localStorage.** *(Filed medium; upgraded — verification showed the meta-territory palisade ring, placed at run start from each player's own localStorage and included in the state hash, desyncs essentially ANY two organic players at the first hash exchange, ~1s in.)* The join message carries only `{name, town}` (`src/mp/LockstepClient.ts:127`); difficulty mutates global `Balance`, which the snapshot never carries, so difficulty-divergent pairs re-diverge after every recovery — a permanent loop. Aggravator found in verification: the MP restore path *overwrites the local player's persistent research save with the peer's* (`src/game/RunSuspend.ts:482`), a durable meta-progress clobber. The MP restore also skips the single-player contractId guard, so `?mp=dev` cross-contract snapshots land buildings on foreign terrain.

### Tier 3 — HIGH: suspend/resume loses sim state (hurts single-player AND makes MP recovery worse)

**H8. The suspend envelope drops every new boss/variant/rail field — restoring a boss run makes it unwinnable.** `src/game/RunSuspend.ts:536-590` — capture/restore still uses the old enemy shape (`{edge, thief, wrecker, activationDelay}` only), while this range added `eliteKind: 'railcar'`, `variantId`, `boltDamageMult`, `bossGroup*`, `bossComponent*`, and scripted rail routes to `Enemy.ts`. After any restore mid-boss-fight: bolt damage multipliers reset to 1, the boss-defeat event can never fire (and boss contracts disable wave-securing, so the run is *permanently unsecurable*), boss-group degradation goes inert, and a railcar loses its route and stalls forever. The MP resync path pushes this exact envelope every 30 ticks, so recovery during a boss fight is lossy and re-divergent. One lens correctly notes the railcar content is currently era-locked for plain players — but the e1-baron suspend gap, the imminent E2 milestone, and MP recovery correctness keep this high.

**H9. Harvest RNG and gold-seam state are excluded from the snapshot; restore redraws seams from each client's diverged RNG.** `src/game/RunSuspend.ts:429-432` instruments only the waves and upgrades RNG streams; `HarvestSystem` owns a third seeded stream (`src/systems/HarvestSystem.ts:51`), and restore just calls `harvestSystem.reset()` (`RunSuspend.ts:476`), re-rolling the seam layout from the *local* stream at its current call count with zero node state (remaining gold, respawn timers) captured. In MP recovery the two clients roll different layouts → divergent panning gold → hash mismatch → the recovery loop again, on the core income mechanic. In single-player, every wave-boundary resume silently reshuffles the seams and resurrects depleted ones at full capacity — a save-fidelity gap and a mild suspend/reload exploit.
