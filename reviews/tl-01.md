## What it does
Adds an **anonymous, opt-out run-statistics beacon** that fires once per completed run (`run_ended`) and a Cloudflare Pages Function (`/api/telemetry`) that validates + aggregates it. The payload carries only gameplay/perf shape — `contract, waves, duration, upgradesTaken, tier, frameP95, deviceClass, buildHash, nonce` — and NO identifiers. The `nonce` is a random 16-byte hex rotated **monthly** (dedup only, not a stable user id). A Settings toggle "Share anonymous run stats" (default ON) with an inline disclosure lets players opt out; opt-out is honored before any POST and survives localStorage-write failure. In dev builds (`__APP_BUILD__ === 'dev'`) the client does not POST unless `gr.telemetry.devSend.v1 === '1'`, so local play/e2e never hits the wire uninstructed. The server rejects identifier-shaped payloads (recursive `IDENTIFIER_KEYS` scan → 400), enforces a CORS allowlist + 4KB cap + strict per-field validation, and when KV is **unbound** accepts+validates but stores nothing (`stored:false`); when bound it writes only counters/buckets with a SHA-256 monthly dedup key. Telemetry failures are swallowed and can never affect the run-return flow (`keepalive:true`, try/catch).

## Findings
- **F-tl01-1 (non-blocking BUT go-live BLOCKER — binding-name mismatch, owner/attended decision):** `functions/api/telemetry.ts` reads `context.env.**TELEMETRY**` (only), but the owner cleared the KV gate by binding the namespace as **`ACCOUNTS`** (BACKLOG §Assay Office line 95: "KV namespace created + bound as `ACCOUNTS` … TL-01 production ingest UNBLOCKED on next deploy"). VERIFIED: `TelemetryEnv = { TELEMETRY?: KVNamespaceLike }` — no `ACCOUNTS`. So on next deploy the endpoint will still hit `if (!env.TELEMETRY) return stored:false` → **silently no-store**, and "see it alive immediately" will NOT happen. Fix is one of: (a) minimal + reversible — change the read to `context.env.TELEMETRY ?? context.env.ACCOUNTS` (accepts either; unblocks now, prefers a dedicated binding later); (b) rename the read to `ACCOUNTS` (couples telemetry to the accounts namespace — keys are already `telemetry:*` prefixed so no collision, but it's an architecture choice); or (c) owner adds a second binding named `TELEMETRY` on the Pages project. **This is an owner/attended call (which namespace telemetry lives in) — NOT fire-rewired autonomously.** The merged slice is production-safe either way (validates, no-stores when its binding is absent).
