## What it does

`scripts/probe-plain-boot-console.mjs` opens a browser on a plain `/` boot at 1280×800 and 390×844,
prints every console message by type, and exits 1 on any warn/error. Drains quote its output **as
evidence**. Until this slice its base URL was:

```js
const baseURL = process.argv[2] ?? 'http://127.0.0.1:5188';
```

No ownership check at all. Run unattended with no argument, it reported a clean-or-dirty boot for
*whatever tree happened to be serving 5188* — and a drain would quote that as proof of its own
slice. That is the same defect that produced s1077's false P0 on the rehearsal rig.

The slice is three files, +31/−3:

```js
const ROOT = path.resolve(path.dirname(fileURLToPath(import.meta.url)), '..');
if (process.argv[2]) throw new Error('Positional base URL is unsupported; use PROBE_BASE=<url> instead.');
const baseURL = resolveBase('PROBE_BASE', { root: ROOT });
```

**All four authored rulings honored, checked one by one:**

1. ✅ **Default DELETED, not moved** — `grep 5188` over the merged file returns nothing. The literal

2. ✅ **No second `lsof` parser** — resolution imports the shipped `resolveBase` from
   `rehearsal/base-url.mjs`. A duplicate parser would have been the third copy of that logic, which

3. ✅ **Resolved BEFORE `chromium.launch()`** — verified by reading, not by the test: resolve is

## Findings

### F-1091-1 — the ordering guard proves fail-closed, not ordering (non-blocking, corrective recommended)

The first test is named **`rejects an unset PROBE_BASE before launching a browser`**, and the goal
leaf cites resolve-before-launch as a deliverable. The test does not check that. It asserts only
`status !== 0` and `stderr =~ /PROBE_BASE/`.

**Measured, not argued.** Moving `const browser = await chromium.launch();` to sit *above* the
resolve and re-running the guard:

```
--- ORDERING MUTATION: chromium.launch() now runs BEFORE resolveBase ---
rc = 0
✔ rejects an unset PROBE_BASE before launching a browser (206ms)
✔ rejects a positional base URL with a PROBE_BASE directive (149ms)
ℹ tests 2  ℹ pass 2  ℹ fail 0
```

**2/2 green while a browser leaks before every throw** — including the test whose name claims
otherwise. The script still fails closed (that part is genuinely guarded), so this is not a
correctness defect today: ordering on main is correct, verified by reading. The gap is that
*nothing defends it*, so a future edit reintroduces the leak silently.

This is the class's own shape for the third time — rf-27 cured a hardcoded default, rf-28 found its
guard could not see the unset branch, and now rf-29's guard cannot see the ordering claim it is
cited for. Recommended: assert the child process emits no browser artifact before the throw (e.g.
that the failure occurs faster than a launch, or that no `chromium.launch` is reachable), as a
one-test corrective. **Recorded as rf-30 in BACKLOG.**
