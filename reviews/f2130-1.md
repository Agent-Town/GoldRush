## VERDICT: MERGED — the cure is real, proved by a red control I ran myself, and it takes nothing away.

## What it does

`scripts/gr-sim.mjs readOrders` previously wrote a stderr line on a rejected submission and
`continue`d, waiting for another stdin line without re-emitting anything on stdout. The turn loop
awaits `readOrders` before `advanceToTurn()`, so a **reactive** client — one that writes only in
response to stdout — had nothing left to react to and the run deadlocked forever. Stream clients
were unaffected, which is why this survived so long.

Both rejection paths (JSON-parse failure and semantic refusal) now funnel through one new
`rejectOrders(reason, sim)` helper that writes the **unchanged** stderr line first and then
re-emits `sim.currentTurn().view` on stdout. The client sees the same view again — no progress —
and can answer it. Nine lines in `gr-sim.mjs`, plus a 56-line regression in `gr-sim.test.mjs`.

This is the master's **option (b)**, not the preferred (a). See F-2132-1 below.

### The one non-obvious risk, closed by reading the code

Option (b) calls `sim.currentTurn()` on the rejection path, and `currentTurn()` → `makeTurn()` is
**not** a pure getter — `HeadlessContractSim.ts:1444-1447` writes four instance fields
(`lastTurnWave`, `lastTurnOfferKey`, `lastSurpriseSeq`, `lastTurnSecurePending`) that
`advanceToTurn()` at `:1148-1151` reads to decide when to emit the next turn. An extra write could
in principle suppress a later turn emission.

It cannot, and the proof is two facts rather than a test:

1. **No sim time passes.** `readOrders` blocks the turn loop, so `this.step()` is not called between
   the last emitted view and the rejection. Wave, offer key and secure-pending recompute identically.
2. **A rejected submit cannot mutate standing orders.** `StandingOrders.submit()` is all-or-nothing —
   every rejection arm (`:154`, `:162`, `:167`, `:172`, `:182`) returns *before* `this.records = ...`
   at `:193`. So `snapshotStandingOrders()` is unchanged and `latestSurpriseSeq(orders)` recomputes
   to the same value. The partial-apply case that would have been dangerous does not exist.

The four writes are therefore idempotent on this path. Empirically corroborated: the new test asserts
the re-emitted view is byte-identical to the prior one (`repeatedView === true`) and passes, and
`agent-reels` asserts two tapes byte-identical across a run with an invalid line prefixed.

## Findings

### F-2132-1 — the protocol says "rejected" only by repeating itself (NON-BLOCKING, no corrective)

The runner took option **(b)** where the master marked **(a)** preferred. The master permits (b)
"only if you can show the transcript is unchanged for valid-order runs", and that condition is met
and measured — so this is **within contract**, not a violation.

But the two options are not equivalent for a future consumer. Option (a) would have emitted a
distinguishable top-level `rejected` key; option (b) emits a view that is byte-identical to the
previous one. A client can therefore only *infer* rejection from stdout — by noticing the view did
not advance — and must read **stderr** to learn *why*. That is a working protocol (it is exactly what
the new test does) and it has the merit of adding no new message shape, but it means the rejection
reason is not available on the same channel as the data.

Filed non-blocking and with **no corrective queued**: the behaviour is correct, the master allowed
it, and re-opening a settled 9-line protocol choice to swap a working mechanism for a preferred one
is scope invention. The next task that needs a machine-readable rejection reason on stdout should
cite this finding rather than rediscover it.

### F-2132-2 — the runner's node-guards tally was already stale when written (NON-BLOCKING, self-resolving)

The run report gives `476 pass, 3 fail, 2 skip` and attributes one red to "the stale `e2-incline`
same-game report on the dispatched lane base". That red was **cured on main by s2131** (F-2131-2,
regenerated at `95a4e0275`) while this run was in flight, so the lane base carried a defect main no
longer has. The other two reds it names are external-contention failures. Recorded so the next
reader does not chase a red that no longer exists; nothing owed.
