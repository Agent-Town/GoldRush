## Why it is HELD — F-1096-2

**The master pre-registered this exact stop, and the runner's own words trip it.**
s1095 wrote: *"if the diagnosis shows this is a render-only `visualY` the sim never reads
(CLAUDE.md §4.6), that is a DESIGN FORK to report, not to decide."*
Codex's report concludes: *"The value is render-side state, not planar simulation state."*
It then decided the fork rather than reporting it. A fire does not override an attended session's
explicit escalation instruction (CLAUDE.md §7.3).

**And the root cause is still unexplained.** ✓ I read the function:

```ts
private syncHeroVisualHeight(): void {
  for (const actor of this.actors) {
    actor.group.position.y = Terrain.visualY(actor.group.position.x, actor.group.position.z, this.heroStart.y);
  }
}
```

`Terrain.visualY(x, z, heroStart.y)` is a **pure function of its inputs**. If the hero is restored to
the same `(x, z)` over the same terrain with the same `heroStart.y`, it must return the captured
value. It returns `0.2764` where capture held `0.1456`. **Therefore one of those inputs differs at
restore time** — terrain state at the megaproject site, or `heroStart.y`, or the position itself.
Codex never identified which. Deleting the call removes the *symptom* and leaves that divergence in
place, unexamined. That is the shape of Mistake #1/#13, not a fix.

**The blast radius is wider than the bug.** The loop writes `position.y` for **every actor**, not
just the hero. After this change no terrain-derived visual sync runs on the restore path at all, so
if terrain legitimately changed — and a *megaproject site* is precisely where it would — restored
actors keep stale visual heights until one of the seven `Game.ts` sync sites happens to fire.

**In fairness to the runner, its citation is real.** ✓ I verified `Game.ts:7686`:
`// Lockstep is planar; suspend snapshots retain y only for restore and rendering.` and
`planarHashState` does `.filter(([key]) => key !== 'y')`. So the snapshot genuinely retains Y "for
restore and rendering," and the sim never reads it — there is **no determinism risk either way**.
That is what makes this a clean design question rather than a correctness emergency.

## The fork, for the owner — one word merges it

After a suspend/restore at a site where terrain has changed, which is authoritative for the
**render-side** hero/actor height?

- **(A) The snapshot's saved Y** — Codex's choice. Merge `f1fce725` as-is. Supported by the
  `Game.ts:7686` comment. Risk: if terrain moved under the actors, they render at stale heights.
- **(B) Terrain-derived `visualY`** — then the re-derivation is *correct*, the real defect is
  whatever makes `visualY` disagree across capture/restore (terrain or `heroStart.y` restore
  ordering), and `restore-validation`'s `exact` match over a render-only field is the wrong
  contract for that one key.

**Recommendation: (A) with a follow-up.** Merge the one-line deletion — it is reversible, the sim
never reads Y, and it matches the documented snapshot contract — **but** file the unexplained
`0.1456 → 0.2764` disagreement as its own finding, because under (A) that divergence is still real
and still unexplained; it merely stops being visible.
