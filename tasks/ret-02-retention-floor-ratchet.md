2. **The ratchet would never have false-redded — measured across the ledger's WHOLE history, not asserted.** `git log --format=%h -- logs/task-stats.jsonl` returns **123 commits**; replaying the row count across all 123 gives **45 → 229 rows with ZERO decreases**. 3. **⚠️ THE OBVIOUS OBJECTION WAS CHECKED AND IT DOES NOT APPLY — do not re-derive it.** §4.10b explicitly permits **compaction of tracked files**, and a lawful compaction would shrink the ledger and red a ratchet. 4. **⚠️ THE SIMPLE VERSION OF THE CURE HAS A HOLE, AND THIS IS WHY SCOPE 1 IS NOT WHAT F-1243-3 RECOMMENDED.** F-1243-3's recommendation was, verbatim, to assert the count never decreases *"versus `git show HEAD:logs/task-stats.jsonl`"*. Prototyped: it catches arms A and B correctly. **But `HEAD` is not a high-water mark — it is whatever was committed last.** The ledger is committed by **fires, as bookkeeping, at fire START, before any gate runs** (`git log -6 -- logs/task-stats.jsonl` shows `s1243: lock ACTIVE …`, `s1240: lock ACTIVE …`, `s1239: runner bookkeeping …`). **So the realistic accident — a stale-base merge or bad script truncates the ledger, and the next fire's lock commit blesses it — moves the baseline DOWN to the truncated value, permanently, and the ratchet then passes forever.** A guard that can be silently disarmed by the ordinary bookkeeping sequence is not a ratchet; it is a floor with extra steps.
5. **The fix for that hole is cheap, and its cost was measured.** Baseline = the **maximum** row count over the last N commits touching the ledger, not HEAD's count. Measured over **N=20**: baseline **229**, wall cost **159 ms**. That survives a single blessing event (the realistic one) and still tracks lawful growth.

**Net: the invariant is right, the denominator is a decaying constant, and the naive repair can be disarmed by a lock commit. This task replaces the constant with a high-water mark — and keeps the floor, because git history is not always available.**
